# transformers-tuning

[![CI](https://github.com/pierrehanne/transformers-tuning/actions/workflows/ci.yml/badge.svg)](https://github.com/pierrehanne/transformers-tuning/actions/workflows/ci.yml)
[![Documentation](https://github.com/pierrehanne/transformers-tuning/actions/workflows/pages.yml/badge.svg)](https://pierrehanne.github.io/transformers-tuning/)

The idea is to implement and demonstrate different ways to leverage parameter-efficient
fine-tuning (PEFT) techniques to fine-tune language models.

This repository is a runnable companion to Hugging Face's
[PEFT methods overview](https://huggingface.co/docs/peft/main/methods/overview). It provides one
training command and a registry of representative methods from every major PEFT family. The
implementations use PyTorch through `transformers` and `peft`; the point is to expose correct,
customizable training recipes without duplicating the well-tested adapter kernels.

## Quick start

Install the project with [uv](https://docs.astral.sh/uv/):

```bash
uv sync --extra dev
uv run peft-train --method lora --max-samples 100
```

List all options:

```bash
uv run peft-train --help
```

The default example fine-tunes `HuggingFaceTB/SmolLM2-135M` on English quotations and writes
only the adapter checkpoint to `artifacts/adapter`. Change the model, dataset, text column, or
projection names from the command line:

```bash
uv run peft-train \
  --method ia3 \
  --model HuggingFaceTB/SmolLM2-135M \
  --dataset Abirate/english_quotes \
  --text-column quote \
  --target-modules q_proj,v_proj
```

Target-module names are architecture-specific. Inspect `model.named_modules()` or the model
documentation when moving away from the default architecture. Soft-prompt and LayerNorm methods
ignore `--target-modules`. `trainable_tokens` assumes an `embed_tokens` embedding module and uses
token id `0`; edit that configuration for newly added tokens in a real application. AdaLoRA's
rank schedule is initialized for 1,000 steps and should be matched to the actual training run.

## Implemented methods

All methods live in `src/transformers_tuning/methods.py` and are selected with `--method`.

| CLI name | Technique | What is trained |
|---|---|---|
| `lora` | LoRA | Two low-rank matrices per selected weight |
| `rslora` | Rank-stabilized LoRA | LoRA with rank-stable scaling |
| `dora` | DoRA | Low-rank direction plus weight magnitude |
| `adalora` | AdaLoRA | A dynamically allocated low-rank budget |
| `loha` | LoHa | Hadamard products of low-rank matrices |
| `lokr` | LoKr | Kronecker-product factors |
| `vera` | VeRA | Scaling vectors over shared frozen projections |
| `ia3` | IA³ | Activation scaling vectors |
| `oft` | OFT | Orthogonal transforms |
| `boft` | BOFT | Butterfly-factorized orthogonal transforms |
| `hra` | HRA | Products of Householder reflections |
| `fourierft` | FourierFT | Sparse Fourier coefficients |
| `prompt_tuning` | Prompt tuning | Virtual input-token embeddings |
| `prefix_tuning` | Prefix tuning | Virtual key/value prefixes at every layer |
| `p_tuning` | P-tuning | Virtual tokens generated by a prompt encoder |
| `ln_tuning` | LayerNorm tuning | LayerNorm scale and bias parameters |
| `trainable_tokens` | Trainable tokens | Selected rows of the token embedding matrix |

QLoRA is not a separate adapter: it is LoRA applied to a frozen 4-bit quantized base model. Use it
when the base model does not fit in accelerator memory; it requires a supported accelerator and a
quantization backend such as bitsandbytes, so it is intentionally not forced into this portable
CPU/MPS example. LoRA initializers such as PiSSA and LoftQ are similarly configuration choices,
not separate training methods.

## Trade-offs and when to use each technique

| Technique | Strengths | Costs / limitations | Use it when |
|---|---|---|---|
| LoRA | Mature, robust, mergeable, broadly supported | More parameters than the smallest methods; rank needs tuning | You want the safest general-purpose baseline |
| RS-LoRA | Better behavior as rank grows | Little benefit at very low rank | LoRA underfits and you plan to raise rank |
| DoRA | Often improves low-rank quality | Extra magnitude parameters and training/inference overhead | Quality matters more than maximum simplicity |
| AdaLoRA | Spends rank where it helps most | Schedule-sensitive and harder to reproduce | A strict parameter budget justifies more tuning effort |
| LoHa | Expressive for a small checkpoint | Less ecosystem support and intuition than LoRA | LoRA capacity is insufficient, especially for vision/diffusion |
| LoKr | Efficient on large matrix or convolution shapes | Factor choices are architecture-sensitive | Adapting vision/diffusion models or very large projections |
| VeRA | Extremely small task-specific checkpoints | Shared random projections constrain capacity | Serving many adapters with minimal storage |
| IA³ | Among the fewest trainable parameters | Usually less expressive; feed-forward targets need model-specific setup | Many tiny adapters or very limited training memory |
| OFT | Preserves hyperspherical geometry and can generalize well | Shape constraints and more specialized kernels | Pretrained feature preservation is especially important |
| BOFT | More parameter-efficient and expressive than basic OFT | More hyperparameters and less mature tooling | OFT is promising but its adapter is too large |
| HRA | Compact orthogonal updates | Newer method with less benchmark and tooling coverage | Exploring orthogonal adaptation under a tight budget |
| FourierFT | Very small sparse updates | Frequency count is shape-sensitive and support is narrower | Extreme parameter efficiency is the main constraint |
| Prompt tuning | Tiny, simple, and easy to swap | Consumes context; quality improves mainly with large models | The task can be steered with a learned input prompt |
| Prefix tuning | More expressive than input-only prompts | Per-layer prefixes consume cache/context and add latency | Generation tasks need more control than prompt tuning provides |
| P-tuning | Prompt encoder improves expressivity | More moving parts; still limited versus weight adapters | NLU-style tasks and learned prompts are a good fit |
| LayerNorm tuning | Almost no added architecture | Limited capacity and architecture-dependent results | The downstream shift is mild and LayerNorms carry useful adaptation |
| Trainable tokens | Changes only chosen vocabulary entries | Cannot teach broad behavior; token ids must be managed carefully | Adding domain tokens, control tokens, or a few new concepts |
| QLoRA | Makes large-model tuning possible on modest VRAM | Slower, hardware/backend-dependent, and quantization can reduce quality | LoRA is suitable but the full-precision base model does not fit |

A practical decision order is: try prompting first; use prompt tuning if learned context is enough;
start weight adaptation with LoRA; move to QLoRA for memory pressure, RS-LoRA/DoRA for more quality,
or IA³/VeRA for smaller per-task storage. Choose the newer factorized, orthogonal, or spectral methods
only when their specific constraint matches the workload and benchmarks confirm the gain.

## Development

```bash
uv run ruff check .
uv run ruff format --check .
uv run pytest
```

The tests build every configuration without downloading a model, which makes validation fast and
deterministic. For a production experiment, also validate the chosen adapter against the exact
model architecture and compare task quality, peak memory, training throughput, checkpoint size,
and inference latency against full fine-tuning and a LoRA baseline.

The project also includes an [Astro documentation site](https://pierrehanne.github.io/transformers-tuning/),
pre-commit hooks, CI across supported Python versions, and tag-driven GitHub releases. See
[CONTRIBUTING.md](CONTRIBUTING.md) for local setup, validation, and release instructions.
